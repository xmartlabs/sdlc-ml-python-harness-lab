# ADR-0003: Record a hashable trial condition (harness fingerprint) per run

- **Status:** Accepted
- **Date:** 2026-07-07
- **Deciders:** Marcos Soto (with Claude Code)
- **Related:** `docs/roadmap-local-webapp.md` (Phases 5–7), `memory/context.md`,
  `src/harness_lab_app/provenance.py`

## Context

The lab is being turned into a scientific instrument to evaluate the
*engineering harness* (skills + docs + hooks + agents) as the independent
variable across cases, prompts, and models. To compare trials and, later, run
ablation studies, each run must record the exact **condition** it ran under.

Before this change, `metadata.json` recorded which skills/subagents were
*available* (by name) but not their versions, nor the model settings, prompt,
or case content. Two trials run days apart with an edited skill looked
identical, so results were not reliably comparable and ablations were not
attributable.

Two forces shaped the design: causal attribution requires **ablation** (toggle
one factor, re-run, compare) rather than observing a single run; and local
models at temperature > 0 make reproducibility **statistical** (N repetitions,
mean ± spread), not deterministic replay.

## Decision

We will compute and store a hashable **trial condition manifest** in each run's
`metadata.json`, via `src/harness_lab_app/provenance.py`, called from
`scripts/bench_run.py:write_metadata` (so both the CLI and web flows get it).

- `condition_hash` — deterministic id of the experimental **arm**, computed over
  the agent-facing harness (skills-lock content hashes + agent file hashes +
  governance-doc hashes + hook file hashes, rolled into `harness_hash`), the
  model settings (executor/planner model, temperature, context tokens), the
  prompt **template** hash, and the case (`task.yaml`) hash.
- `harness_fingerprint` — the component hashes plus `opencode` and conductor
  plugin versions.
- `model_condition` — executor/planner model, temperature, context tokens,
  gateway alias.
- Provenance-only fields recorded but **excluded** from `condition_hash`:
  `lab_git_commit`, `harness_git_dirty`, `runner_image`.

Skill hashes are reused from `skills-lock.json`'s canonical `computedHash`
(generated by `skills_sync`), not recomputed. The logic lives in the app
package (not in `scripts/`) so the web app can later group/compare runs by
`condition_hash`. Enrichment is best-effort: if provenance cannot be computed,
the base metadata is still written and the run never fails.

## Consequences

- Easier: reps of one arm share a `condition_hash` (→ group cells, measure
  variance); a diff of two fingerprints is the exact description of an ablation;
  every trial is auditable back to a harness state and lab commit.
- The prompt hash uses the template (`prompt_source`), not the generated
  `prompt.md`, which embeds per-run ids and would otherwise break arm stability.
- New fields must be classified: does it change the *arm* (→ into
  `compute_condition_hash`) or only document provenance (→ manifest only)?
- Gateway-side model enforcement (LiteLLM "build" profile: output cap, routing)
  lives in a separate repo and is not fully captured locally; the gateway alias
  is recorded so it stays traceable.
- For rigorous experiments the harness should be committed first so
  `harness_git_dirty=false` and trials attribute to a clean `lab_git_commit`.

## Alternatives considered

- **Recompute skill hashes from disk** instead of reusing `skills-lock.json` —
  rejected: duplicates the `skills_sync` hashing and can diverge from the
  canonical lock; `harness_git_dirty` already flags drift vs the committed tree.
- **Include `lab_git_commit` in `condition_hash`** — rejected: every unrelated
  commit would invalidate all prior arms, making cells impossible to accumulate;
  the agent-facing harness is the arm, lab code is provenance.
- **Hash the generated `prompt.md`** — rejected: it embeds run id/session/model,
  so identical arms would never match.
