# ADR-0082: Models are compared on one case by the checks they pass, not by pass rate

- **Status:** Accepted
- **Date:** 2026-11-15
- **Deciders:** Marcos Soto
- **Amends:** [ADR-0002](0002-celery-docker-per-run-execution.md) (one run at a
  time), for runs that rewrite nothing shared
- **Related:** [ADR-0040](0040-subject-validation-mode.md),
  [ADR-0051](0051-the-harness-ladder-is-one-family-of-single-factor-experiments.md),
  [ADR-0066](0066-harness-and-model-vary-together-only-in-a-full-grid.md),
  [ADR-0080](0080-a-long-run-shows-its-progress-and-asks-before-it-is-cut.md)

## Context

When a new frontier model ships, the question is: how does it do on the case the
last one did? The 3D game cases (chess, racing, the open city) were built to answer
it. The lab had no direct way to ask:

- `harness_evaluation` refuses arms that differ by model: the model is held fixed, so
  that a difference can be attributed to the harness.
- `harness_by_model` varies the model, but only as a full grid with a harness factor.
  It answers a different question (ADR-0066).
- `subject_validation` accepts arms that differ only by harness and model, with no
  control, reported per arm and never pooled (ADR-0040). Its wizard, though, is built
  to validate a tool someone wrote: a new case, staged skills.

The arms of these cases are rarely passed outright: chess3d-v1 has 40 checks, and a
strong run stops near 31. Read as pass/fail, every model scores 0%, and the
comparison says nothing.

Two models also cannot share a harness. Claude models run under `claude`; local and
gateway models run under `opencode`.

## Decision

1. **A model comparison is a `subject_validation` experiment** on one case, with one
   arm per model. Each arm fixes `harness` and `executor_model` (and, for claude, the
   reasoning effort). The prompt variant, repetitions and step budget are shared by
   every arm. Its subject is `model comparison on <case>`. No new mode and no new
   column.
2. **Every comparison on a case is filed in the family `models-<case_id>`** (ADR-0051).
   The experiments page lists them together, so the next model's comparison is read
   next to the last one. A launched experiment keeps its configuration (the launch
   lock), so a new model means a new experiment in the same family, not an arm added
   to an old one.
3. **The reading is checks, not pass rate.**
   `GET /api/experiments/{id}/model-comparison` (`model_comparison.py`) returns, per
   arm and per run:
   - the final checks passed and counted;
   - the checks after each phase, from the per-step reward;
   - `test_pass_rate`, cost and minutes.

   Everything is read from the scores and the validation each run already records.
   An unknown cost (a local model) is `null`, never zero. The page shows it on any
   experiment of a `models-` family.
4. **A wizard builds it**: Evaluate → Compare models (`/evaluate/compare-models`).
   You pick one case, then two to four harness + model pairs. The steps and the
   variant default to the case's.
5. **Runs may execute two at a time.** One at a time stays the default. *Two at a
   time* (`POST …/launch` with `parallel: 2`) interleaves the runs by arm and
   alternates them between two queues, `runs` and `runs-parallel`, each served by a
   worker of concurrency 1. Each lane then gets one model, so a fast cloud model
   finishes, and can be played, while a slow local one is still going. ADR-0002 kept
   one lane because `bench_run.py` writes shared state in the lab's tree. Here is how
   each piece of that state is handled:
   - `BENCH_CONTEXT.md`, which names the active run and which opencode reads every
     session, is now per run: each agent container binds
     `data/runs/<id>/bench_context.md` over it. The repo's file is never written by
     a container run.
   - The native skill views are regenerated by every governed run. That rewrite is
     serialised by a file lock (`data/app/skill-views.lock`); between two runs that
     ablate nothing, it writes the same thing.
   - A skill ablation changes the views for every run, so a launch that asks for two
     at a time refuses any arm with `skills_disabled` or `skills_extra`.

   Two at a time is accepted only for an experiment of a `models-` family, and only
   when the launch can publish to the second lane. Otherwise it is refused rather
   than quietly run one at a time. The API also refuses it unless a worker is
   *known* to serve `runs-parallel`: no answer from the workers counts as no. That
   way half the runs never sit `pending` unseen. `GET /api/runs/lanes` lets the
   wizard offer the option only when the lane is confirmed.
6. **Sandboxes have their own queue.** Terminal, Desktop and Play go to
   `interactive`, served by their own worker. On the run lane they queued behind a
   run of several hours, so a finished game could not be played while another run
   was going.
7. **A restarting worker spares the runs other workers drive.** Every worker
   reconciles `running` rows on boot. With three workers, a restart of one used to
   fail, and stop the container of, a run another was still executing. Rows that
   some live worker reports as an active `execute_run` (`runs_in_flight`) are now
   left alone. The check fails closed: when no worker answers the inspection, the
   reconciliation touches nothing, because "unknown" is not "nothing running". The
   health panel's heal button reconciles once the workers answer.

## Consequences

- A new frontier model is compared against an older one in a few clicks, on exactly
  the settings the older one ran with, and the result sits beside every earlier
  comparison on that case.
- The comparison reports per-model results only. It makes no causal claim about the
  harness, because each arm is a harness + model pair. When the harnesses differ,
  so does the agent loop, and the table names both.
- Run one at a time, three models on a phased game case take several hours. Two at a
  time roughly halves the wall time. It costs twice the token quota per hour and two
  runner containers at once (8 GB for two game runs), with the CPU shared. Two runs
  on the same local model take turns on its GPU and gain little. The wizard says so
  next to the choice.
- Two at a time is offered by the model comparison only. Every other launch, and any
  relaunch from the experiment page, stays on the one lane.
- The host-mode worker (`make app-host`, subprocess backend) serves `runs` and
  `interactive` on one process and has no second lane: without containers there is
  no per-run `BENCH_CONTEXT.md`.
- The run progress strip also reads harnesses that write no event stream (opencode),
  from each step's plain log: turns, times and the last action, with the cost
  reported as unknown.
